## 构建目标

使数据集分配可复现。在已初始化的工作区实现 `stage1.go`。随附 CLI 调用你的实现，不导入参考解答。

## 理解运行机制

分片把标识符分配到桶。FNV-1a32 从 2166136261 开始，对每个 UTF-8 字节执行异或，再乘以 16777619，并按 32 位回绕，最后对分片数取模。Go 的 `hash/fnv` 实现了这一原语，学习重点在于定义并测试其外围的标识契约。

四分片情况下，样本标识符分别落入 case-d→0、case-c→1、case-b→2、case-a→3。重新排列输入会改变桶内顺序，但不会改变某个标识符所属的桶。不要断言每个桶大小相同：确定性分配不保证负载均衡。

拒绝空标识符、重复标识符，以及超出 1..1024 的分片数。随附持久化存储还会对有序输入记录计算指纹，包括提示词、预期答案和已记录响应。预测或分片数发生变化时，需要使用另一个存储，否则恢复的运行可能把两次实验的结果混在一起，却仍沿用一个表面上的数据集名称。

空分区无需租约，也不会加入持久化的活动分片列表；覆盖率仍计算每个实际用例。一个记录、四个桶的样本只有一个活动分片，不会凭空生成四个已完成任务。

## 实现契约

```go
func Partition(ids []string, shards int) ([][]string, error)
```

保留 `types.go` 中的公开签名和错误定义。拒绝调用时，必须保持调用方先前状态不变。阅读[项目 API](../../../API.md)，了解最终交付物的文件与进程边界。

## 实现提示

先分配请求的全部桶，跟踪已经出现的标识符，对字节计算哈希，并将每项追加到恰好一个桶。保持 ID 原样，规范化可能合并原本不同的用例。

## 检查失败边界

分别将样本划为 4 个和 3 个桶。哪些用例 ID 会移动？说明为何即使分片归属不变，只修改提示词也会改变整次运行的指纹。
