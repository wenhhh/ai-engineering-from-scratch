## 1. 协议时代模型（The era model）

| 术语（Term） | 含义（Meaning） |
|---|---|
| 现代（Modern） | 2026-07-28 及后续版本，版本、身份及能力通过每请求元数据传递。 |
| 旧版（Legacy） | 2025-11-25 及更早版本，连接以创建会话的 `initialize` 握手开始。 |
| 双时代（Dual-era） | 同时支持两者，在解析前明确判定协议时代的实现。 |

版本标识采用 YYYY-MM-DD 日期形式，记录最近一次引入向后不兼容变化的日期。版本可处于 Draft（正在制定）、Current（正在使用，仍可接受向后兼容的修改；本快照中为 2026-07-28）或 Final（已完成并冻结）状态。

版本历史，按从新到旧排列：

| 版本（Revision） | 主要变化（Headline changes） |
|---|---|
| 2026-07-28 | 无状态核心；移除 `initialize` 和会话；引入 `server/discover`、多轮往返请求（MRTR）、`resultType`、`subscriptions/listen`；任务移入扩展；弃用 roots、sampling、logging 和动态客户端注册；增加可缓存结果、必需 HTTP 请求头、错误码分配政策与功能生命周期政策。 |
| 2025-11-25 | 图标；通过 `WWW-Authenticate` 增量请求权限范围同意；工具命名指引；URL 模式信息征询；采样中的工具调用；推荐客户端 ID 元数据文档；实验性任务；输入校验错误归为工具执行错误（SEP-1303）；默认使用 JSON Schema 2020-12；治理与 SDK 分级。 |
| 2025-06-18 | 结构化工具输出（`outputSchema`、`structuredContent`）；工具结果中的资源链接；信息征询；带受保护资源元数据的 OAuth 资源服务器分类；必需资源指示器；HTTP 上的 `MCP-Protocol-Version` 请求头；移除 JSON-RPC 批处理。 |
| 2025-03-26 | Streamable HTTP 替代 HTTP+SSE；OAuth 2.1 授权框架；工具注解；音频内容；补全能力。 |
| 2024-11-05 | 首个公开版本，提供 stdio 与 HTTP+SSE 传输，以及 `initialize` 握手。 |

2026-07-28 移除的内容，授课时不得将其当作该版本的现有机制：

- `initialize` 请求与 `notifications/initialized`（SEP-2575）。
- 协议会话与 `Mcp-Session-Id` 请求头（SEP-2567）。
- Streamable HTTP 的 GET 流端点与会话 `DELETE`。
- `resources/subscribe` 和 `resources/unsubscribe`，由 `subscriptions/listen` 替代。
- `ping`、`logging/setLevel`、`notifications/roots/list_changed`。
- SSE 恢复与重新交付机制，包括 `Last-Event-ID` 和 SSE 事件 ID。
- 任何流上的服务器主动请求，由 MRTR 替代。
- 核心协议中的任务，移入 `io.modelcontextprotocol/tasks` 并重新设计，不再包含 `tasks/result` 或 `tasks/list`。
- `notifications/elicitation/complete` 和 URL 模式信息征询的 `elicitationId` 字段。
- `-32002`（资源未找到，现为 `-32602`）及 `-32042`（需要 URL 信息征询）错误码。

## 2. 消息（Messages）

所有消息遵循 JSON-RPC 2.0，并应用以下 MCP 规则：

- **请求（Request）**：`{"jsonrpc":"2.0","id":<string|integer>,"method":...,"params":{...}}`。id 不得（MUST NOT）为 null，也不得（MUST NOT）重复仍在等待回复的 id。
- **结果响应（Result response）**：与请求使用相同 id；`result` 必须（MUST）包含 `resultType`。
  - `"complete"`：最终内容。
  - `"input_required"`：`InputRequiredResult`，即第 7 节的 MRTR。
  - 只有通过能力声明后，扩展才可以（MAY）增加取值，例如任务扩展增加 `"task"`。
  - 客户端必须（MUST）将无法识别的 `resultType` 视为无效；对于旧服务器未提供的 `resultType`，必须（MUST）按 `"complete"` 处理。
- **错误响应（Error response）**：`{"jsonrpc":"2.0","id":...,"error":{"code":<int>,"message":...,"data":...}}`。只有无法从损坏请求读取 id 时，才省略它。
- **通知（Notification）**：包含 `method` 和可选 `params`，不得（MUST NOT）包含 id，接收方也不得（MUST NOT）回复。
- 不支持 JSON-RPC 批处理，该机制已于 2025-06-18 移除。Streamable HTTP 每个 POST 正文恰好携带一个请求或通知。

## 3. `_meta` 与每请求协议字段（_meta and per-request protocol fields）

键名由可选前缀与名称组成：前缀为点分标签加 `/`，推荐采用反向 DNS；名称以字母或数字开头和结尾。前缀的第二个标签为 `modelcontextprotocol` 或 `mcp` 时，保留给 MCP 使用，例如 `io.modelcontextprotocol/`、`dev.mcp/`；`com.example.mcp/` 则不保留。

下表列出客户端请求使用的字段。必需字段缺失会使请求格式无效，返回 JSON-RPC `-32602`，HTTP 上同时返回 `400 Bad Request`：

| 键（Key） | 是否必需（Required） | 含义（Meaning） |
|---|---|---|
| `io.modelcontextprotocol/protocolVersion` | 是 | 例如 `"2026-07-28"` |
| `io.modelcontextprotocol/clientCapabilities` | 是 | 与当前请求相关的能力，可以为 `{}` |
| `io.modelcontextprotocol/clientInfo` | 否，但应提供（SHOULD） | `Implementation`，包含 `name`、`version`，以及可选 `title`、`description`、`websiteUrl`、`icons` |
| `io.modelcontextprotocol/logLevel` | 否 | 当前请求的最低日志级别，对应已弃用日志功能 |
| `progressToken` | 否 | 使请求接收 `notifications/progress` |

服务器应（SHOULD）在结果的 `result._meta` 中包含 `io.modelcontextprotocol/serverInfo`。`clientInfo` 和 `serverInfo` 都是发送方自报字段，只用于展示、日志与调试，不得用于安全决策。

其他保留键包括 `io.modelcontextprotocol/subscriptionId`，用于 `subscriptions/listen` 流中的每条消息；以及 `traceparent`、`tracestate`、`baggage`，承载符合 W3C Trace Context 与 W3C Baggage 格式的 OpenTelemetry 上下文。这些裸键名按 SEP-414 显式保留，与通常的命名空间前缀做法不同。

最小现代请求示例：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {"location": "Pune"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {"name": "ExampleClient", "version": "1.0.0"}
    }
  }
}
```

## 4. 无状态性（Statelessness）

- 处理请求所需的信息全部在请求中。服务器不得（MUST NOT）依赖同一连接的先前请求推断能力、版本或身份。
- stdio 进程或 HTTP 连接本身不构成会话，客户端可以在同一传输通道交错发送不相关请求。
- 跨请求状态，例如长时间工作、购物车或浏览器上下文，必须（MUST）通过客户端在每个相关请求中传入的显式标识引用：服务器在工具结果中返回句柄，客户端再把它作为普通参数传回（SEP-2567）。句柄命名状态，本身不授予访问能力；每次调用都要针对句柄校验调用方授权，保持句柄不透明，在工具描述中说明存续时间，并通过工具执行错误报告过期句柄。
- `tools/list`、`resources/list` 和 `prompts/list` 不得（MUST NOT）因连接不同，或作为其他请求的副作用而变化；可以（MAY）根据当前请求呈现的授权变化。
- 原因：任意副本都能处理任意请求，重试可以路由到其他副本，负载均衡器无须粘性路由。这里保证的是路由不依赖旧连接，不能据此推断任意有副作用的操作都可安全重复执行。

## 5. 错误码（Error codes）

| 代码（Code） | 名称（Name） | 用途（Use） |
|---|---|---|
| -32700 | 解析错误（Parse error） | JSON 无效 |
| -32600 | 请求无效（Invalid Request） | 不是有效请求对象 |
| -32601 | 方法未找到（Method not found） | 未知方法，HTTP 返回 `404 Not Found` |
| -32602 | 参数无效（Invalid params） | 未知工具、缺少必需 `_meta`、资源未找到、提示词名无效或缺少提示词参数、游标无效、日志级别无效 |
| -32603 | 内部错误（Internal error） | 服务器内部故障 |
| -32020 | 请求头不匹配（HeaderMismatch） | HTTP 请求头与正文不一致，或缺少必需请求头；HTTP 返回 `400` |
| -32021 | 缺少客户端必需能力（MissingRequiredClientCapability） | `data.requiredCapabilities` 列出客户端需要声明的内容；HTTP 返回 `400` |
| -32022 | 不支持的协议版本（UnsupportedProtocolVersion） | 携带列表 `data.supported` 和 `data.requested`；HTTP 返回 `400` |

2026-07-28 的分配政策：

- `-32000` 至 `-32019` 属于旧版区间，不得（MUST NOT）分配新代码，新实现也不应（SHOULD NOT）使用。
- `-32020` 至 `-32099` 保留给 MCP 规范，禁止发送此区间中尚未定义的代码。
- 实现该版本时，不得（MUST NOT）发送 `-32002` 或 `-32042`；客户端仍应（SHOULD）把旧服务器返回的 `-32002` 解释为“资源未找到”。
- 应用自定义代码应（SHOULD）位于 `-32768` 至 `-32000` 整个区间之外。

工具的两个错误通道，是本路线重点考查的区别：

1. **协议错误（Protocol errors）**，采用 JSON-RPC `error`：未知工具（`-32602`）、请求不满足 `CallToolRequest` 模式，以及服务器错误。
2. **工具执行错误（Tool execution errors）**，采用带有 `isError: true` 和解释性 `content` 的正常结果：API 失败、日期格式错误或取值越界等输入校验失败、业务规则拒绝，以及句柄过期。这些信息返回模型，使其能够自行修正（SEP-1303，2025-11-25）。

未知工具使用 `-32602`；`-32601` 对应未知方法。参数违反工具自己的 `inputSchema` 时，返回工具执行错误，不能使用 `-32602`。

## 6. `server/discover` 与版本协商（server/discover and version negotiation）

- 服务器必须（MUST）实现 `server/discover`，该请求仅携带标准 `_meta`。
- `DiscoverResult` 是可缓存结果，包含 `resultType`、`supportedVersions`、`capabilities`、可选 `instructions`（给模型的自然语言指引）、`_meta["io.modelcontextprotocol/serverInfo"]`、`ttlMs` 和 `cacheScope`。
- 客户端调用发现是可选的。它可以直接发送任意请求，在收到 `UnsupportedProtocolVersionError` 后从 `data.supported` 选择版本重试。
- 在 stdio 上，双时代客户端应（SHOULD）先用 `server/discover` 探测：`DiscoverResult` 表示现代；`-32022` 等可识别现代错误表示需要其他版本，不能回退；其他错误或超时则按旧版处理，回退 `initialize`。回退判断不得（MUST NOT）绑定到某个特定错误码。
- 在 HTTP 上，双时代客户端先尝试现代请求，再检查 `400` 正文：可识别的现代 JSON-RPC 错误表示现代服务器，其他情况按旧版处理。
- 按服务器进程（stdio）或源站（HTTP）缓存时代判断。
- 仅支持现代协议的服务器，应（SHOULD）在对 `initialize` 返回的错误中列出自己支持的版本。

服务器能力：`tools {listChanged}`、`resources {listChanged, subscribe}`、`prompts {listChanged}`、`completions {}`、`logging {}`（已弃用）、`extensions {...}`、`experimental {...}`。
客户端能力：`elicitation {form, url}`、`sampling {context, tools}`（已弃用）、`roots {}`（已弃用）、`extensions {...}`、`experimental {...}`。
服务器不得（MUST NOT）依赖客户端未在当前请求中声明的能力；需要这种能力时，返回 `-32021`。

## 7. 多轮往返请求（Multi Round-Trip Requests，MRTR）

MRTR 替代所有服务器主动发起的请求，属于破坏性变化（SEP-2322）。

1. 客户端发送请求。
2. 服务器返回 `{"resultType":"input_required","inputRequests":{...},"requestState":"..."}`，其中必须（MUST）至少包含 `inputRequests` 或 `requestState` 之一。
3. `inputRequests` 将服务器自选键映射到请求对象，每项类型只能是 `elicitation/create`、`sampling/createMessage` 或 `roots/list` 之一。服务器不得（MUST NOT）包含客户端没有声明对应能力的请求类型。
4. 客户端收集答案，**使用新的 JSON-RPC id 重试原请求**，增加使用相同键的 `params.inputResponses`，并逐字节回传 `params.requestState`。服务器未提供 `requestState` 时，客户端不得（MUST NOT）自行添加。
5. 服务器返回最终结果，或通过另一个 `InputRequiredResult` 再次请求输入。

只有 `tools/call`、`prompts/get` 和 `resources/read` 可以返回 `InputRequiredResult`。
`requestState` 属于攻击者可控制的输入；只要它影响授权、资源访问或业务逻辑，就应使用 HMAC 或 AEAD 保护，并绑定经过认证的主体、短有效期及原请求摘要。单次使用限制必须在服务器端执行。
`input_required` 结果及 MRTR 重试均不得缓存。

## 8. 通知、订阅、进度与取消（Notifications, subscriptions, progress, cancellation）

- `subscriptions/listen` 打开长时间存续的流。`params.notifications` 是过滤条件，包含布尔值 `toolsListChanged`、`promptsListChanged`、`resourcesListChanged`，以及 URI 列表 `resourceSubscriptions`。服务器不得（MUST NOT）发送未请求的类型。
- 首条消息必须（MUST）是 `notifications/subscriptions/acknowledged`，回传服务器实际接受的类型子集。流中每条消息携带 `_meta["io.modelcontextprotocol/subscriptionId"]`，取值为 `subscriptions/listen` 请求的 JSON-RPC id。
- 订阅流通知包括 `notifications/tools/list_changed`、`notifications/prompts/list_changed`、`notifications/resources/list_changed`，以及带有 `uri` 的 `notifications/resources/updated`。
- 请求级通知 `notifications/progress` 与 `notifications/message` 只通过其所属请求的响应流发送，不得混入监听流。
- 进度：客户端设置 `_meta.progressToken`，类型为字符串或整数，在活动请求之间唯一；`notifications/progress` 携带 `progressToken`、严格递增的 `progress`，以及可选 `total` 和 `message`。请求完成时停止通知。
- 取消：Streamable HTTP 通过关闭对应请求的 SSE 响应流表达取消，不另发消息；stdio 客户端发送包含 `requestId` 和可选 `reason` 的 `notifications/cancelled`。服务器只有在拆除 `subscriptions/listen` 流时，才发送 `notifications/cancelled`。忽略已取消请求的迟到响应，取消竞争是正常情况。
- 每个请求都应（SHOULD）设置超时；即使持续收到进度，也应有不可无限延长的最大时限。
- 服务器正常结束订阅时，应（SHOULD）用 `subscriptions/listen` 结果作答，包含 `resultType: "complete"`，并在 `_meta` 中携带订阅 id。

## 9. 传输（Transports）

**标准输入输出（stdio）**

- 客户端将服务器作为子进程启动。JSON-RPC 按换行分帧，消息内部不嵌入真实换行。
- `stdout` 只承载 MCP 消息，`stderr` 承载日志，日志未必表示错误。
- 服务器不向 `stdout` 写入请求。全部元数据内联在 `_meta` 中，没有请求头层。
- 关闭：客户端关闭 `stdin`，等待退出，再按需升级为 SIGTERM 或 SIGKILL。发生意外退出时，客户端重启服务器、处理丢失请求的重试，并重新发送 `subscriptions/listen`；有副作用的调用仍需先判断重复执行风险。
- 授权：stdio 实现不应（SHOULD NOT）使用 OAuth 流程，应从环境读取凭据。

**可流式 HTTP（Streamable HTTP）**

- 使用一个接受 POST 的 MCP 端点，例如 `https://example.com/mcp`，每条客户端消息单独 POST。
- `Accept` 同时列出 `application/json` 和 `text/event-stream`。请求响应可以是单个 JSON 对象，也可以是仅属于该请求的 SSE 流；客户端必须（MUST）支持两者。
- 通知 POST 返回 `202 Accepted`，不带正文。
- SSE 流先携带请求相关通知，最后发送最终响应。服务器不得（MUST NOT）在任何流上发送请求。
- 没有 GET 端点、`Mcp-Session-Id` 或 `Last-Event-ID`。仅支持现代协议的服务器对 GET 或 DELETE 返回 `405`，忽略会话及事件 id 请求头。
- 安全：校验 `Origin`，存在且无效时返回 `403`，防止 DNS 重绑定；本地运行时绑定 `127.0.0.1`；执行身份认证。
- 必需头：每个 POST 的 `MCP-Protocol-Version` 应与 `_meta` 中的版本相同，否则返回 `400` 和 `-32020`；每个请求包含 `Mcp-Method`；`tools/call`、`resources/read`、`prompts/get` 还需 `Mcp-Name`，值来自 `params.name` 或 `params.uri`。通知 POST 的未明确要求见第 17 节。
- 工具输入模式中的 `x-mcp-header` 可将基本类型参数镜像到 `Mcp-Param-{Name}`：仅允许整数、字符串或布尔值，不允许 `number`，且必须是从模式根部静态可达的属性。服务器作者不应（SHOULD NOT）标记密码、API 密钥、令牌或个人信息等敏感参数，因为中间层可以看到头值。非纯 ASCII 值使用哨兵形式 `=?base64?...?=`。HTTP 客户端必须（MUST）将 `x-mcp-header` 定义不符合约束的工具从自己的 `tools/list` 结果排除。服务器必须（MUST）拒绝与正文不一致的头，错误码为 `-32020`。
- 状态码：不支持的版本为 `400` 加 `-32022`；缺少能力为 `400` 加 `-32021`；未知方法为 `404` 加 `-32601`；令牌缺失或无效为 `401`；权限范围不足为 `403`。
- 2024-11-05 的 HTTP+SSE 传输自 2025-03-26 起已弃用（SEP-2596），最早可在 SEP-2596 达到 Final 后三个月移除。

## 10. 服务器原语（Server primitives）

控制模型：工具**由模型控制**，资源**由应用驱动**，提示词**由用户控制**。

**工具（Tools）**

- `tools/list` 支持分页与缓存，并应（SHOULD）采用确定性排序，以利于客户端缓存和 LLM 提示词缓存命中。
- 工具定义包含 `name`、可选 `title`、`description`、可选 `icons`、`inputSchema`、可选 `outputSchema`、可选 `annotations` 和可选 `_meta`。inputSchema 必须是 JSON Schema 对象，不能为 null；无参数时使用 `{"type":"object","additionalProperties":false}`。
- 名称应（SHOULD）由 1 至 128 个 `A-Za-z0-9_-.` 字符组成，区分大小写，并在服务器内唯一。聚合器应（SHOULD）用服务器标识加前缀；`serverInfo.name` 不保证唯一。
- 注解是提示，除非服务器可信，否则必须（MUST）视为不可信输入：`title`、`readOnlyHint`（默认 false）、`destructiveHint`（默认 true，仅非只读时有意义）、`idempotentHint`（默认 false）、`openWorldHint`（默认 true）。
- `tools/call` 参数包括 `name`、`arguments`，以及重试时的 `inputResponses` 和 `requestState`。
- `CallToolResult` 包含 `content`（内容块列表）、可选 `structuredContent` 和可选 `isError`。structuredContent 可以是任意 JSON 值；存在 `outputSchema` 时必须符合它，并应（SHOULD）将相同数据序列化到文本块。
- 内容块包括 `text`；带 `data` 和 `mimeType` 的 `image`；`audio`；带 `uri`、`name`、可选 `description` 和 `mimeType` 的 `resource_link`；以及嵌入内容 `resource`。它们均可包含 `annotations`，其中 `audience` 为 `user` 或 `assistant`，`priority` 为 0 至 1，并可指定 `lastModified`。
- 应（SHOULD）让人能够拒绝调用。服务器必须（MUST）校验输入、执行访问控制、限流并处理输出中的不安全内容。客户端应（SHOULD）确认敏感操作、调用前展示输入、校验结果、设置超时并记录使用情况。

**资源（Resources）**

- 使用 `resources/list`、`resources/read` 和 `resources/templates/list`，后者采用 RFC 6570 URI 模板。内容形式为 `{uri, mimeType, text}` 或 `{uri, mimeType, blob}`。
- 能力为 `resources {listChanged, subscribe}`，更新通过带 `resourceSubscriptions` 的 `subscriptions/listen` 接收。
- 未找到返回 `-32602`，不能用空 `contents` 数组代替；内部错误为 `-32603`；兼容接收旧版 `-32002`。
- URI 方案包括：仅在客户端能直接获取时使用的 `https://`；`file://`，未必对应真实文件系统，但映射到文件时须规范化路径防止穿越；`git://`；以及符合 RFC 3986 的自定义方案。

**提示词（Prompts）**

- 使用 `prompts/list` 和带 `arguments` 的 `prompts/get`；结果包含 `messages`，各消息具有 `role`，取值为 `user` 或 `assistant`，以及一个内容块。
- 错误：名称无效或缺少必需参数为 `-32602`，内部错误为 `-32603`。

**补全（Completion）**：`completion/complete` 携带 `ref`，可以是按名称指定的 `ref/prompt`，或按 URI／模板指定的 `ref/resource`；此外还有 `argument {name, value}` 和 `context.arguments`。返回最多 100 个 `values`，以及 `total`、`hasMore`。对应能力为 `completions {}`。

**分页（Pagination）**：使用不透明的 `cursor` 和 `nextCursor`，由服务器决定页大小；空字符串是合法游标，无效游标返回 `-32602`。

**缓存（Caching）**（SEP-2549）：`server/discover`、`tools/list`、`prompts/list`、`resources/list`、`resources/templates/list` 和 `resources/read` 的 `resultType: "complete"` 结果，必须（MUST）携带 `ttlMs`（大于等于 0 的整数）和 `cacheScope`（`"public"` 或 `"private"`）。`ttlMs` 是新鲜度提示，不能当作轮询间隔；列表变更通知立即使对应缓存失效。`"private"` 缓存绝不跨授权上下文共享。`cacheScope` 从不承担访问控制。

## 11. 客户端功能（Client features）

**信息征询（Elicitation）**，通过 MRTR 的 `inputRequests` 传递，方法为 `elicitation/create`。

- 表单模式包含可选的 `mode: "form"`、`message` 和 `requestedSchema`，后者是由基本属性组成的扁平对象。URL 模式包含 `mode: "url"`、`message` 和 `url`，用于 OAuth 同意授权或支付等带外页面，使敏感数据不经过客户端。
- `ElicitResult.action` 可以是 `accept`（表单模式带 `content`）、`decline` 或 `cancel`。
- 客户端能力为 `elicitation {form, url}`。

## 12. 授权，适用于 HTTP 传输（Authorization, HTTP transports）

- 授权框架整体可选。HTTP 实现应（SHOULD）遵循；stdio 不应（SHOULD NOT）采用，应使用环境中的凭据。
- 角色：MCP 服务器充当 OAuth 2.1 资源服务器，MCP 客户端充当 OAuth 2.1 客户端，授权服务器负责签发令牌。
- MCP 服务器必须（MUST）实现受保护资源元数据（RFC 9728），在 `authorization_servers` 中至少列出一项。通过 `401` 响应的 `WWW-Authenticate: Bearer resource_metadata="..."` 发现，或按 well-known URI 查找：先访问路径专用 `/.well-known/oauth-protected-resource/<path>`，再访问根级位置。
- 授权服务器元数据遵循 RFC 8414 或 OpenID Connect Discovery。issuer 含路径时，依次尝试 `/.well-known/oauth-authorization-server/<path>`、`/.well-known/openid-configuration/<path>`、`<path>/.well-known/openid-configuration`。元数据的 `issuer` 必须（MUST）等于构造 URL 时使用的 issuer。
- 必须使用 PKCE，具备能力时使用 `S256`；缺少 `code_challenge_methods_supported` 时，客户端必须（MUST）拒绝继续。
- 资源指示器（RFC 8707）：授权请求和令牌请求都携带 `resource`，值为目标服务器的规范 URI，包含方案与主机，无片段，按约定不带末尾斜杠。即使授权服务器忽略该值，客户端也要发送。
- 每个 HTTP 请求都通过 `Authorization: Bearer <token>` 传递令牌，不放在查询字符串中。
- 服务器必须（MUST）校验受众，确认令牌签发给自己；不得（MUST NOT）接受或透传面向其他受众的令牌。上游 API 使用独立令牌，禁止令牌透传。
- issuer 校验（RFC 9207）：客户端重定向前记录期望 issuer，对返回的 `iss` 作精确比较，不进行规范化；包括错误响应在内，只要不匹配就拒绝，以防混淆攻击。
- 权限范围：优先使用首个 `WWW-Authenticate` 挑战中的 `scope`，否则使用 `scopes_supported`。运行中权限不足时返回 `403` 与 `error="insufficient_scope"`，在一次挑战中列出完整所需权限。客户端以原权限与新增权限的并集提升授权，并限制重试次数。
- 刷新令牌：不能假定一定签发；公共客户端的刷新令牌需要轮换；服务器不应强制要求 `offline_access`。
- 状态码：`401` 表示令牌缺失或无效，`403` 表示权限范围不足，`400` 表示授权请求格式错误。

**客户端注册优先顺序（Client registration priority）**：（1）预注册凭据；（2）授权服务器声明 `client_id_metadata_document_supported` 时使用客户端 ID 元数据文档；（3）存在 `registration_endpoint` 时回退到已弃用的动态客户端注册；（4）询问用户。

- CIMD：`client_id` 是带路径的 HTTPS URL，指向至少包含 `client_id`（与该 URL 完全相等）、`client_name` 和 `redirect_uris` 的 JSON。授权服务器获取并校验文档、检查重定向 URI，并防护 SSRF。仅包含 localhost 重定向的文档需要额外提示，并始终展示重定向主机名。CIMD 标识可以跨授权服务器使用。
- DCR：客户端必须（MUST）发送 `application_type`，桌面、CLI 和 localhost 应用为 `native`，远程浏览器应用为 `web`。
- 授权服务器绑定：持久化凭据按 issuer 隔离，不能用于另一个授权服务器；授权服务器变化时重新注册。
- 混淆代理：使用静态 client id 的 MCP 代理，在将请求转向第三方授权服务器之前，必须（MUST）为每个动态注册客户端取得用户同意。
- 通信：授权服务器所有端点均使用 HTTPS；重定向 URI 为 localhost 或 HTTPS，并精确注册；使用并校验 `state`。

**授权扩展（Authorization extensions）**：不会默认启用，通过 `extensions` 协商。OAuth 客户端凭据扩展适用于 CI、守护进程等机器客户端；企业托管授权扩展适用于集中式身份提供方（IdP）策略。

## 13. 授权之外的安全检查（Security checklist beyond authorization）

- 工具描述、注解、图标和结果都是进入模型的不可信输入，可能携带投毒、提示词注入，或通过定义变更实施 rug pull。
- 图标只接受 `https:` 或 `data:` URI；获取时不携带凭据，要求与服务器同源，并将 SVG 视为潜在可执行内容。
- JSON Schema 不自动解引用网络 `$ref`；只有显式启用、配置主机允许列表、拒绝私网地址并设置超时后，才获取远程引用。限制组合关键字的资源开销，防止拒绝服务。
- Streamable HTTP 需要 `Origin` 校验、本地绑定和身份认证。
- MRTR 的 `requestState` 需要完整性保护、主体绑定、有效期和原请求绑定。
- 日志不包含凭据、秘密或个人数据。
- 缓存中 `"public"` 结果可跨用户和令牌共享，但各原语仍须独立执行访问控制。

## 14. 扩展（Extensions）

- 标识符：遵循 `_meta` 命名规则，形式为 `{vendor-prefix}/{name}`。官方扩展使用 `io.modelcontextprotocol/`，第三方使用自己拥有的反向域名，例如 `com.example/my-extension`。
- 协商：客户端在每个请求的 `io.modelcontextprotocol/clientCapabilities.extensions` 中声明支持，服务器则在 `server/discover` 的 `capabilities.extensions` 中声明。值为对应扩展的设置对象，`{}` 表示支持且没有额外设置。
- 仅一方支持扩展时，支持方回退到核心行为，或用相应错误拒绝请求。扩展默认关闭，必须明确选择启用。破坏性变更需使用新标识，例如增加 `-v2`。
- 流程见 SEP-2133：提出 Extensions Track SEP，在官方 SDK 中提供参考实现，并由核心维护者审阅。实验性仓库使用 `experimental-ext-` 前缀，归工作组或兴趣组管理。
- 官方扩展：
  - **任务（Tasks）**，`io.modelcontextprotocol/tasks`（SEP-2663）：服务器可以对已声明支持的请求返回 `resultType: "task"`，即带有 `taskId`、状态、TTL 及建议轮询间隔的 `CreateTaskResult`。客户端用 `tasks/get` 轮询，以 `tasks/update` 的 `inputResponses` 提交执行中所需输入，也可以用 `tasks/cancel` 请求协作式取消。状态包括 `working`、`input_required`、携带 `result` 的 `completed`、携带 `error` 的 `failed`，以及 `cancelled`。不存在 `tasks/result` 或 `tasks/list`。
  - **MCP 应用（MCP Apps）**，`io.modelcontextprotocol/ui`（SEP-1865）：工具的 `_meta.ui` 包含 `resourceUri`，指向通过普通 `resources/read` 获取、类型为 `text/html;profile=mcp-app` 的 `ui://` 资源；还可包含 `visibility`，默认 `["model", "app"]`。不包含 `"model"` 时，宿主不得（MUST NOT）向智能体列出该工具；不包含 `"app"` 时，宿主必须（MUST）拒绝来自应用的 `tools/call`。UI 资源本身的 `_meta.ui` 位于 `resources/read` 的内容条目上，包含 `csp` 对象，其中可选 `connectDomains`、`resourceDomains`、`frameDomains`、`baseUriDomains` 分别列出源；还可包含 `permissions` 对象，其中可选 `camera`、`microphone`、`geolocation`、`clipboardWrite` 的值为 `{}`。宿主必须（MUST）依据声明域构造 CSP，不得（MUST NOT）允许未声明域，可以（MAY）进一步收紧；完全省略 `csp` 时，必须（MUST）采用禁止出站连接的严格默认值 `connect-src 'none'`。宿主可以（MAY）授予 `permissions` 请求，但应用不应（SHOULD NOT）假定已经获准。视图在沙箱 iframe 中运行，网页宿主通过不同源的沙箱代理包装它；应用与宿主使用含 `ui/` 方法的 JSON-RPC 方言通信，由应用的 `ui/initialize` 开始，这与已移除的核心 `initialize` 无关。对于未支持扩展的宿主，工具仍返回有意义的文本。
  - **通过 MCP 提供技能（Skills over MCP）**，`io.modelcontextprotocol/skills`（SEP-2640）：使用 `skills/list` 和 `skills/get`，通过 `resources/read` 提供技能文件；读取 `SKILL.md` 不意味着激活技能。技能内容属于不可信输入，应标明来源服务器；是否加载由明确的用户策略决定。宿主应（SHOULD）允许用户先检查技能，不得（MUST NOT）在未逐技能获得批准时，让技能内容触发宿主端代码执行；除非用户批准该权限授予，否则必须（MUST）忽略 MCP 技能中 `allowed-tools` 等扩大权限的元数据。
  - **授权扩展（Authorization extensions）**，`ext-auth`：OAuth 客户端凭据和企业托管授权。

## 15. 治理、生命周期与生态（Governance, lifecycle, and ecosystem）

- 功能生命周期（SEP-2596）：Active（启用）、Deprecated（已弃用，仍有规范定义，必须有迁移路径，且从弃用版本发布起至少保留十二个月）、Removed（已移除）。最早可移除版本为窗口结束当日或之后发布的首个版本，是否真正移除由核心维护者决定。后续取代它的 SEP 可以恢复已弃用功能。
- SEP：采用 PR 流程，文件位于 `seps/`（SEP-1850）；治理见 SEP-932，工作组与兴趣组见 SEP-1302；Final SEP 要求符合性测试（SEP-2484）。
- SDK 分级（SEP-1730）：Tier 1 通过 100% 符合性测试，在规范发布前提供相应功能，两工作日内分诊，七天内修复严重缺陷；Tier 2 通过 80%，六个月内提供新功能；Tier 3 属于实验级。所有等级都不强制实现扩展。符合性持续失败四周后，SDK 会按相应规则降级。
- 注册目录在本快照中处于预览期，只保存指向 npm、PyPI、Docker 等软件包或远程 URL 的元数据 `server.json`。反向 DNS 命名空间通过 GitHub、DNS 或 HTTP 挑战验证，例如 `io.github.user/server`、`com.example/server`。只接收公开服务器；私有服务器可部署实现相同 OpenAPI 规范的自有目录。目录面向聚合器，不供宿主直接消费；安全扫描交由软件包平台和聚合器。`server.json` 的模式版本与运行时 MCP 协议版本相互独立。
- 治理归属：MCP 是 Linux Foundation 旗下 Agentic AI Foundation 的项目。
- 规模：上游引用 MCP 博客 2026-07-28 发布文章，当时 Tier 1 SDK 合计每月下载量接近五亿，TypeScript 与 Python SDK 各自累计下载量均已超过十亿。这里保留原文历史数据，不将它当作本次汉化时的新统计。

## 16. 容易混淆的考点（Traps the exam can exploit）

| 错误认识（Wrong belief） | 2026-07-28 对应规则（Correct fact） |
|---|---|
| 连接先发送 `initialize`。 | 没有握手；每个请求通过 `_meta` 携带版本和能力；客户端可选调用 `server/discover`，服务器必须实现它。 |
| 会话 id 在调用之间保存状态。 | 没有协议会话，使用服务器生成的显式句柄，并作为参数传递。 |

| 参数不符合工具模式时返回 `-32602`。 | 返回带 `isError: true` 的工具执行错误，让模型读取反馈并修正。 |
| 服务器把采样或信息征询请求主动推给客户端。 | 使用 MRTR：先返回 `input_required`，客户端再携带 `inputResponses` 和新 id 重试。 |
| 重试沿用原请求 id。 | 重试必须（MUST）使用新 id，并原样回传 `requestState`。 |
| 用 `resources/subscribe` 监视资源。 | 使用带 `resourceSubscriptions` 的 `subscriptions/listen`。 |
| 工具注解是强制执行的保证。 | 它们只是提示，提供方不可信时按不可信输入处理。 |
| `cacheScope: "public"` 保护数据。 | 它允许跨用户共享，访问控制另行执行。 |
| 进度和日志通知通过监听流到达。 | 它们只通过所属请求自己的响应流发送。 |

| 新服务器应使用 `-32001` 表达自定义错误。 | `-32000` 至 `-32019` 属于旧版区间；`-32020` 至 `-32099` 保留给规范；应用代码位于 `-32768` 至 `-32000` 之外。 |

| 流可以使用 `Last-Event-ID` 恢复。 | 该机制已移除。断流后需要使用新 id 重新发起请求；有副作用时先判断幂等性、去重和结果是否未知。 |

## 17. 编写时处理的来源冲突（Source conflicts resolved during the build）

两份一手页面冲突时，应以规范性记录为准：消息结构使用 `schema.ts`；判断 2026-07-28 存在哪些机制时，使用变更日志和对应规范页面；历史 SEP 草案不能覆盖已发布版本。下表标为“未明确”的问题，不能包装成只有唯一规定的考题。
