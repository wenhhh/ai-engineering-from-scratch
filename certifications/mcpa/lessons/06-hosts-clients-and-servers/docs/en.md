# 宿主、客户端与服务器：MCP 的进程拓扑（Hosts, Clients, and Servers: MCP's Process Topology）

> 宿主通过每台服务器对应的独立客户端进行通信。这种一对一绑定构成 MCP 信任边界的基础，也是聚合多台服务器的宿主处理名称冲突的起点。

**Type:** Reference
**Languages:** Python
**Prerequisites:** 第 05 课
**Time:** ~45 分钟

## 学习目标（Learning Objectives）

- 列出 MCP 系统的三个参与方：宿主、客户端与服务器，并说明各自职责
- 解释宿主为何为每条服务器连接嵌入一个独立客户端，而不让一个客户端同时处理多台服务器
- 区分本地 stdio 服务器与远程 Streamable HTTP 服务器，说明各自的信任问题实际跨越哪种边界
- 将服务器功能 tools、resources、prompts、completion，以及各项客户端功能，对应到各自的控制方或提供方
- 将多台已连接服务器的工具聚合到一个注册表，用服务器 id 前缀解决名称冲突，并解释为何不能使用服务器自报的 serverInfo.name 作为路由键

## 问题（The Problem）

设想一个同时接入三个系统的助手：文件服务器、笔记服务器和指标服务。每条连接都携带你在前面无状态核心和时代协商课程中见过的请求结构：每个请求注明自己的协议版本和能力，连接不保留跨调用协议状态。但那些课程尚未回答另一个问题：宿主同时与三台服务器通信时，究竟是谁在与谁对话？如果两台服务器用相同方式描述自己，或暴露了同名工具，会发生什么？

一种简单但欠妥的设计，是把三台服务器都塞进一个繁忙的连接对象，由它跟踪哪台服务器发送了什么。这样的设计缺少明确位置记录结果来源，难以阻止一台服务器声明的能力泄漏到发往另一台服务器的调用中；当两台服务器碰巧都自称“primary”时，也无法将其区分。这些都不是罕见边缘情况。任何接入多台 MCP 服务器的宿主都必须解决它们。规范架构通过结构来处理这些问题：固定角色、每对参与方独立连接，以及针对彼此不了解的服务器所规定的名称处理规则，避免仅靠开发者自律。

## 概念（The Concept）

MCP 系统由三个参与方组成，每个角色承担明确而有限的职责。**宿主（Host）**是用户实际运行的单个应用进程，例如聊天助手、IDE 或批处理流水线。宿主创建客户端，决定允许哪些连接存在，在工具运行前执行同意授权检查，并聚合所连接服务器返回的上下文。整个系统中，只有宿主能够看到跨所有已连接服务器的完整信息。

**客户端（Client）**是宿主创建的对象，在连接的整个生命周期内，每个客户端只对应一台服务器。这种约束构成架构隔离的一部分，防止服务器之间的信息相互混入。如果宿主需要连接第二台服务器，就创建第二个客户端，而不复用第一个客户端的连接。拥有三台活动服务器的宿主也拥有三个客户端对象：每个对象连接自己的服务器，在每个请求中填写无状态核心课程所介绍的协议版本与能力，并与其他两个客户端的活动保持隔离。客户端还负责不直接进入报文的记录工作：关联请求 id、跟踪服务器声明的能力，以及确定允许向哪台服务器发送工具调用。

**服务器（Server）**是独立程序，可以位于**本地（Local）**或**远程（Remote）**。本地服务器通常作为子进程启动，通过 stdio 访问；JSON-RPC 消息以换行分隔，没有请求头层，协议元数据全部放在 `_meta` 中。远程服务器通常是通过 Streamable HTTP 访问的常驻服务，每条消息对应一个 POST；除 `_meta` 中的版本外，还需在必需请求头中重复声明协议版本。信任分析应依据服务器实际跨越的边界。本地 stdio 服务器跨越进程边界：通常以同一用户身份运行，直接从环境读取凭据；规范要求 stdio 实现不应运行 OAuth 流程。远程 Streamable HTTP 服务器跨越网络边界：常由不同团队或公司运营，授权框架面向的正是这种传输，包括 bearer 令牌、受保护资源元数据与受众校验。两种边界都不会天然更强；宿主需要逐台分析实际跨越的边界，不能把所有“服务器”当作没有差别的一类。

规范还提出一项值得牢记的设计原则：服务器不应能够读取完整对话，也不应窥见彼此的信息。客户端每次发送请求时，只携带该请求所需内容，不发送宿主的全部历史。不同服务器由不同进程承载，分别与独立客户端对象通信，这种结构用于落实隔离，避免只将其视为礼貌性的约定。

服务器原语按控制方区分。**工具（Tools）**由模型控制：模型依据名称、描述和输入模式决定何时调用。**资源（Resources）**由应用驱动：宿主决定获取哪些资源并放入上下文，资源本身是 URI 与内容。**提示词（Prompts）**由用户控制：用户显式选择模板，而非由模型自行选取。第四项服务器功能**补全（Completion）**为提示词或资源模板提供参数自动补全，由应用驱动，因为用户输入时，决定展示哪些建议的是宿主。客户端功能的方向相反，由服务器向客户端索取内容。**信息征询（Elicitation）**允许服务器在调用过程中向用户请求信息，以 `input_required` 结果交付，客户端通过携带 `inputResponses` 重试来回答；它在当前版本中仍处于完全启用状态。**采样（Sampling）**和 **roots** 则在 2026-07-28 起被弃用：采样让服务器请求客户端代为执行模型补全，新服务器应直接调用大语言模型服务商 API；roots 让客户端声明文件系统边界，新服务器应改为通过工具参数、资源 URI 或服务器配置接收目录。弃用不等于功能已经消失，两者仍然可用；最早可移除它们的版本，必须发布于 2027-07-28 或之后。

当一个宿主接入多台服务器，聚合便成为实际设计问题。工具名称只需要在同一服务器内唯一。两台彼此不了解的服务器都可以暴露名为 `search` 的工具，也可以在 `server/discover` 结果中自报相同的 `serverInfo.name`，因为这个字段由各自运营者填写。如果宿主用这个自报名称索引聚合注册表，或让第二个 `search` 静默覆盖第一个，模型工具调用就可能在无人察觉时被路由到错误服务器。解决办法分两步。首先，注册表条目及所有路由决策，都使用宿主建立连接时自行分配的连接标识，例如配置键或槽位索引；标识必须由宿主控制，不能采用 `serverInfo.name`。其次，两台服务器声明同名工具时，保留第一个 `search` 的原名作为规范条目，给后续冲突工具加上服务器 id 前缀，使两个工具都能通过不同名称访问。无论宿主如何聚合，工具所属服务器仍执行自己的错误规则：未知工具依旧返回 `-32602`，无效参数仍返回工具执行错误，与引入聚合前完全一致。

## 交互实验（Interactive Lab）

图中一个宿主进程包含三个客户端方框，每个分别连接右侧自己的服务器。Files 和 notes 被画为使用 stdio 的本地服务器，并刻意自报相同的 `serverInfo.name`：“primary”。Metrics 被画为使用 Streamable HTTP 的远程服务器，只声明 resources 能力，没有 tools。观察图的底部：由于 files 首先声明 `search`，注册表保留该名称指向 files；notes 的同名工具则以 `notes/search` 暴露。注意，files 与 notes 共同使用的自报名称“primary”从未成为注册表中的路由键。宿主决定如何路由时，不依赖服务器希望如何称呼自己。

## 实践实验（Practice Lab）

打开 `code/main.py`。它仅使用标准库构造三台服务器，不涉及网络或 SDK，但消息结构与 2026-07-28 模式完全对应。`build_host()` 使用三个独立 `Client` 对象，将 `Host` 分别连接到 `files`、`notes` 和 `metrics`，然后调用 `build_registry()` 聚合工具。

```bash
python3 code/main.py
```

将输出与上面的概念部分对照。第一部分并列显示宿主分配的连接 id 与服务器自报名称：files 和 notes 都报告“primary”，说明自报身份不能作为可靠索引。第二部分展示聚合注册表：`search` 映射到 files，`notes/search` 映射到 notes，没有任何工具条目指向 metrics，因为 metrics 从未声明 `tools` 能力，宿主甚至没有向它发送 `tools/list`。之后的逐客户端交互显示每个请求的 `_meta` 和每个结果的 `resultType`。末尾两个条目分别是：通过路由发送但缺少参数的调用，返回 `isError: true`；直接调用 notes 服务器不存在的工具，返回 JSON-RPC 错误 `-32602`。两者都符合前面课程介绍的双错误通道规则。

随后修改并重跑。添加第四台服务器，让它的 `serverInfo.name` 同样与“primary”冲突，但分配新的宿主连接 id，确认注册表仍能按 id 正确路由。也可以让 files 和 notes 再暴露另一组同名工具，确认无须修改 `Host.route`，前缀规则仍然生效。

## 关键术语（Key Terms）

| 术语（Term） | 含义（Meaning） |
|------|---------|
| 宿主（Host） | 用户运行的单个应用进程，负责创建和管理客户端 |
| 客户端（Client） | 宿主创建的对象，在连接生命周期内只绑定一台服务器 |
| 服务器（Server） | 暴露工具、资源和提示词的独立程序，可以是本地 stdio 程序或远程 Streamable HTTP 服务 |
| 本地服务器（Local server） | 通过 stdio 访问的子进程，信任分析围绕进程边界展开 |
| 远程服务器（Remote server） | 通过 Streamable HTTP 访问的服务，信任分析围绕网络边界展开 |
| 控制模型（Control model） | 工具由模型控制，资源由应用驱动，提示词由用户控制 |
| 信息征询（Elicitation） | 允许服务器通过 MRTR 往返向用户请求输入的客户端功能 |
| serverInfo.name | 服务器自报身份，仅用于展示和日志，不能作为路由键 |
| 服务器 id 前缀（Server-id prefix） | 宿主用于区分同名工具的前缀，例如 `notes/search` |
