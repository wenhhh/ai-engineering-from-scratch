# MCP 解决的集成问题（The Integration Problem MCP Solves）

> AI 应用每接入一个系统，都需要一份契约。MCP 让各处契约采用相同结构，使客户端能够使用此前从未见过的服务器。

**Type:** Reference
**Languages:** Python
**Prerequisites:** 第 01 课
**Time:** ~45 minutes

## 学习目标（Learning Objectives）

- 解释 N 乘 M 的集成问题，以及共享协议如何将其降为 N 加 M。
- 说明 MCP 为 AI 应用与外部系统之间的交互标准化了什么，以及有意留给应用决定的部分。
- 分别用一句话说明 MCP 系统参与方和三类服务器原语。
- 将发现请求、工具列表和工具调用读作携带逐请求元数据的普通 JSON-RPC 消息。
- 区分协议错误与工具执行错误，并解释这种区别为何影响模型。

## 问题（The Problem）

过去，将 AI 应用连接到外部系统通常需要编写胶水代码。助手要访问文件、工单队列和数据库，就需要三套集成；每套都自行设计能力描述、参数格式、错误结构和调用权限。第四个系统意味着第四套集成。如果再加入第二个 AI 应用，通常又要重写所有集成，因为为第一个应用编写的内容无法直接适配第二个。

这构成 N 乘 M 的问题。四个应用与六个系统需要二十四套集成，每套都可能发生格式偏移或安全假设模糊。最昂贵的往往是做到第二十套时，以及必须同时理解二十套集成的审查工作。

模型上下文协议（Model Context Protocol，MCP）将 N 乘 M 转化为 N 加 M。每个应用只需实现一次 MCP 客户端，每个系统只需暴露一个 MCP 服务器。现代客户端随后能够使用现代服务器，因为双方采用一致的消息格式、能力描述方式、工具调用方式和结果读取方式。四个应用与六个系统只需十份实现，每增加一个系统再增加一份即可。

## 概念（The Concept）

MCP 是一种协议，负责标准化 AI 应用与为其提供上下文、支持其行动的系统之间的通信：服务器如何描述自己，客户端如何查询服务器提供什么，如何调用工具，以及如何返回结果和错误。MCP 有意不规定模型本身、宿主选用哪个模型、如何构建提示词，或界面应该怎样呈现；这些仍由应用决定。

参与方很少。**宿主（Host）** 是用户使用的应用，例如聊天助手或编辑器。宿主内部的**客户端（Client）** 负责与一个**服务器（Server）** 通信；宿主为每个所用服务器运行一个客户端。服务器提供三类**原语（Primitives）**。**工具（Tools）** 是带名称、说明和模式类型的操作，模型可以决定调用。**资源（Resources）** 是由 URI 标识的可读数据，由应用决定是否加入上下文。**提示词（Prompts）** 是用户主动选择的可复用模板。三者控制方各异：工具由模型控制，资源由应用驱动，提示词由用户控制。

所有消息都采用 JSON-RPC 2.0。请求包含 `id`、`method` 和 `params`；响应携带 `result` 或 `error`，并使用相同的 `id`。在 MCPA 对齐的 2026-07-28 修订版中，每个请求还通过 `params._meta` 携带自己的协议元数据：键 `io.modelcontextprotocol/protocolVersion` 对应协议版本，`io.modelcontextprotocol/clientCapabilities` 对应客户端能力，建议使用 `io.modelcontextprotocol/clientInfo` 提供客户端名称和版本。协议没有起始握手，也没有会话。每个请求独立自足，因此任意服务器副本都能处理。

每个结果均携带 `resultType`。本课先使用 `complete`，表示结果包含最终内容；后续会介绍 `input_required`，用于服务器在完成操作前还需要用户提供信息的情况。

发现机制依靠数据描述能力。客户端调用 `server/discover`，即可获知服务器支持的协议版本、能力和名称；调用 `tools/list`，即可获得各工具的名称、说明及输入模式。客户端无须提前编译这些信息。互操作性的核心因此很直接：今天编写的客户端可以驱动明年编写的服务器，因为服务器通过协议描述自身。

错误分为两类，考试会关注其区别。**协议错误（Protocol error）** 采用 JSON-RPC 错误，表示请求本身有问题；例如调用服务器未提供的工具时，错误码为 `-32602`（Invalid params，参数无效）。**工具执行错误（Tool execution error）** 则是带 `isError: true` 的普通结果，其内容解释工具遇到的问题，例如缺少参数。模型能够读取工具执行错误，并使用修正后的参数重试；协议错误通常无法给模型提供同等丰富的纠正信息。

## 实践实验（Practice Lab）

打开 `code/main.py`。这是不使用网络和 SDK 的标准库模型，消息结构遵循 2026-07-28 模式。它构建两个互不相关的服务器，天气服务与工单服务，以及一个不为任一服务器定制的客户端类。客户端发现服务器、列出工具并调用它们。

```bash
python3 code/main.py
```

将打印的交互与概念部分对照。找到每个请求的 `_meta` 和每个结果的 `resultType`，再找出三种故意构造的失败。调用 `get_forecast` 但不提供城市，会收到带 `isError: true` 的普通结果；调用不存在的工具，会收到 JSON-RPC 错误 `-32602`；声明协议版本为 `1999-01-01` 的请求，会收到 `-32022`，其 `data` 列出服务器实际支持的版本。修改城市，为工单服务器添加第三个工具，再运行；观察客户端无须修改即可发现新能力。

## 关键术语（Key Terms）

| 术语 | 含义 |
|------|------|
| 宿主（Host） | 用户使用的应用，为每个服务器运行一个客户端 |
| 客户端（Client） | 宿主内部与一个服务器通信的组件 |
| 服务器（Server） | 通过 MCP 暴露工具、资源和提示词的程序 |
| 工具（Tool） | 由模型控制，带名称、说明和输入模式的操作 |
| 资源（Resource） | 由应用驱动、通过 URI 标识的可读数据 |
| 提示词（Prompt） | 用户主动选择并控制的模板 |
| `_meta` | 每个请求携带版本、能力与客户端身份的元数据块 |
| `resultType` | 表示结果已完成还是需要更多输入的字段 |
| 协议错误（Protocol error） | 针对请求本身问题的 JSON-RPC 错误，例如未知工具（`-32602`） |
| 工具执行错误（Tool execution error） | 带 `isError: true` 的普通结果，供模型读取并修正 |
