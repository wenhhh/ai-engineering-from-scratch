# MCP 工具调用的风险与安全控制（Risk and Safety Controls for MCP Tool Calls）

> 工具描述会直接进入模型上下文，并可能被理解为指令。因此，即使系统其他部分看起来保护充分，这段文字仍可能成为成本很低的攻击入口。

**Type:** Reference
**Languages:** Python
**Prerequisites:** 第 25 课
**Time:** ~45 分钟

## 学习目标（Learning Objectives）

- 列出正确授权、无状态的 2026-07-28 部署仍面临的攻击面：元数据投毒、获批后篡改、工具遮蔽、混淆代理、令牌透传、requestState 篡改、SSRF、DNS 重绑定、恶意图标和供应链漂移
- 通过哈希固定工具定义，发现后续描述符相对于先前批准版本的变化
- 将工具描述、注解和结果视为可能被模型理解为指令的不可信输入，避免默认认为它们已经经过人工审核
- 阻止令牌透传，使面向 MCP 服务器的凭据不会流向无关上游 API
- 策略导致调用被拒，而请求结构本身无误时，选择 isError 工具执行结果，不发明协议错误码

## 问题（The Problem）

一个客服网关聚合十多台 MCP 服务器，让同一个助手能够搜索工单、读取内部文档，并把已解决问题同步到计费系统。模型眼中的每台服务器都体现为文字：名称、描述、结构定义，以及工具调用返回的内容。协议不判断这些文字是否诚实，只检查消息结构；消息完全符合结构要求，也仍可能对工具行为作出虚假说明。

第 22 课划出了信任边界，第 25 课构建了破坏性操作前的人工同意门禁。两者都不能独立完成全部防护。用户批准的是实际看到的调用，批准环节无法追溯保护模型此前用于选择工具的描述，也无法逐次覆盖那些通常无人审阅的常规非破坏性调用。网关还需要在无人盯守时依然有效的控制，并在问题进入确认对话框之前就发现它。

## 概念（The Concept）

安全与治理需要分层构建。第 22 课说明信任区域，第 23、24 课说明客户端如何证明身份，第 25 课处理用户批准具体操作的时刻。本课补充自动控制层：面对无人逐次审核的调用，以及工具描述已经进入模型上下文、用户还没有看到任何提示的阶段，服务器或网关应自动执行哪些检查？

工具名称、描述、注解、图标和结果，都应按第 22 课的原则视为来自服务器的不可信输入。描述可能嵌入与工具本职无关的指令，例如要求模型额外调用其他工具、把输出转发到其他地方，或对用户隐瞒某个步骤。模型仅凭语气无法可靠区分使用说明和攻击，因此防御不能只寄望于“阅读得更仔细”。工具返回值同样如此：成功且结构正确的 CallToolResult，其可信程度仍取决于提供它的服务器。被攻陷或恶意的服务器可以在普通结果文本中插入指令，与在描述中插入一样容易。静态扫描器可在注册及每次变化时廉价检查可疑措辞，例如要求忽略已有指引或对用户隐藏步骤。但它只起预警作用，不能证明安全：精心改写的攻击可能漏检，合法警告也可能因使用相同短语被误报。命中后应交给审阅者判断，避免把命中或未命中直接当作最终结论。

昨天通过评审的工具，不保证今天仍然相同。所谓获批后篡改（Rug pull），是对已经批准的名称、描述、结构定义或注解进行变更；危险之处在于名称常常不变，后续调用看起来毫无区别。只固定描述文字，会漏掉同样可能改变行为的结构定义或注解变化，因此应规范化并对整个描述符计算哈希：

```python
payload = json.dumps(
    {"name": name, "description": description, "inputSchema": input_schema},
    sort_keys=True, separators=(",", ":"),
)
digest = hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

将摘要与工具的限定名称关联保存。每次刷新时，新出现的键先等待审核；未限定名称发生重复时，应增加命名空间；已有键的摘要变化则表明批准后的定义发生漂移，应隔离工具、等待复审，确认有人查看后才接受新摘要。哈希相等只能证明定义稳定，不能证明定义安全。被投毒的描述符即使固定得再精确，也仍然有毒；因此固定摘要应与描述扫描叠加使用，不能替代它。

两台服务器可能各自暴露名为 search 的工具，彼此并不知道对方存在。网关聚合后若让发现顺序悄悄决定采用哪一个，就产生工具遮蔽（Tool shadowing）：本应发给一台服务器的 search 可能被路由到另一台，请求本身却看不出错误。第 06 课为聚合工具添加服务器标识前缀，第 09 课将易冲突的未限定名称列为清单审阅问题，都是在处理这个风险。批准、审计、哈希固定和路由，应共同引用限定名称，不依赖描述文本或服务器自报的 serverInfo。

代表客户端访问第三方 API 的 MCP 服务器，本身也是 OAuth 客户端，因而成为使用受委托权限行事的代理。混淆代理攻击会诱使它代攻击者使用自己的权限，常涉及共享静态 client id，以及浏览器仍保存的先前合法流程同意 cookie。更常见的一种相关错误是令牌透传：处理器拿到客户端用于向 MCP 服务器认证的 bearer 令牌，又把同一枚令牌转发给无关上游 API。

```json
{
  "http": {"headers": {"Authorization": "Bearer client-bearer-9f2c"}},
  "message": {
    "jsonrpc": "2.0", "id": 5, "method": "tools/call",
    "params": {
      "name": "sync_upstream_ticket",
      "arguments": {"ticket_id": "T-88", "upstream_credential": "client-bearer-9f2c"}
    }
  }
}
```

`arguments.upstream_credential` 与入站 bearer 令牌具有相同字符串值。处理器若将它转发，相当于把一枚仅按 MCP 服务器受众验证过的凭据交给上游 API。解决办法是拒绝透传，另行取得面向上游的凭据。授权安全要求明确规定，服务器必须验证令牌面向自身受众，并且不得在调用上游时透传收到的客户端令牌。

第 14 课详细介绍了多轮往返请求，其 `requestState` 也属于本课威胁清单：它一旦离开服务器，就成为客户端可能修改的输入。不能假定客户端会原样返回。只要 `requestState` 影响授权、资源访问或业务逻辑，就应提供完整性保护，采用签名或具有认证能力的加密方案，绑定已认证主体、较短有效期与原始请求摘要，并在服务器端落实单次使用。

MCP 有多处需要根据他人提供的 URL 获取内容：授权服务器获取 CIMD，客户端跟随 `WWW-Authenticate` 中的 `resource_metadata`，或校验器处理工具 inputSchema 内的 `$ref`。盲目跟随都可能造成服务器端请求伪造。网络引用不能默认无条件解引用；确需获取时，应由显式启用的获取策略保护，设置允许列表，禁止私有与链路本地地址，要求 HTTPS，并限制超时。验证时看似正常的域名，执行请求时可能已解析为内部地址，因此还必须处理解析与连接之间的变化。DNS 重绑定将同样的问题用于本地 HTTP 服务器：第一次解析指向安全地址，后续却指向回环或内部地址。第 19 课的 Origin 检查与本地绑定规则用于防御这类情况。图标还带来图像形式的输入风险：只接受 `https:` 或 `data:` URI，核查与声明服务器的同源要求，并将 SVG 视为可能包含脚本的内容。

供应链风险发生得更早。注册表条目、软件包版本和实际响应请求的端点，是来自不同主体的三项事实；搜索到注册表条目就自动信任，会错误地把三者合为一项。命名空间需要验证其认证所有者，不能只比较字符串前缀，因为相似名称同样可能通过这种检查。软件包或远程来源应按摘要固定，浮动版本标签明天可能指向与评审时不同的字节。准入之后还要持续观察运行中的服务器，因为它可能在获批后增加新工具。上述检查各有作用，不能互相替代。

策略拒绝还必须选择合适的响应通道。请求本身格式有误，例如调用服务器从未注册的工具，应返回 JSON-RPC 协议错误 `-32602`，与第 02 课的未知工具相同。希望模型读取并可能采取行动的拒绝，例如触发速率限制或工具因定义漂移被暂缓，应放入正常结果，设置 `isError: true` 并提供解释，不使用 JSON-RPC 错误，也不临时发明错误码。`-32001` 看似可用，但其所在的 `-32000` 至 `-32019` 范围仅为旧版实现保留；`-32020` 至 `-32099` 则保留给规范。确实需要应用自定义错误码时，必须放在整个 `-32768` 至 `-32000` 范围之外。多数策略拒绝无需新增代码，因为 `isError` 已能承载模型可读、可向用户解释，有时还能据以调整行动的内容。

这些自动控制不依赖每次都有人参与，这正是其价值。将读取不可信输入、接触敏感数据和实施重要操作集中在一个自动步骤，是本清单各类威胁试图利用的路径。应拆开这些环节：先固定描述符以发现变化，进入模型前扫描描述，使用凭据前核查受众，获取网络引用前判断是否允许。这样，一次漏审就不容易直接演变成事故。速率限制、超时，以及在降权沙箱进程中运行处理器，则提供更基础的约束：它们不需要理解攻击语义，也能在上游较复杂的检查漏掉问题时限制损害。

## 实践实验（Practice Lab）

打开 `code/main.py`。`RiskGateway` 最初代理 `search_helpdesk` 与 `sync_upstream_ticket`，随后尝试注册结构定义包含网络 `$ref` 的第三个工具，以及描述含注入指令的第四个工具。

```bash
python3 code/main.py
```

对照概念部分阅读输出。`bulk_import` 的注册结果为 `accepted=False`，网络 `$ref` 使其在进入目录前被拒绝。`draft_reply_wizard` 则显示 `accepted=True`，原因指出命中的可疑短语：工具记录被保留，但立即隔离。请求日志中，第一次 `search_helpdesk` 调用成功；随后 `gateway.observe()` 模拟结构定义改变后的刷新；下一次同名调用返回 `isError: true`，因批准后定义漂移被要求复审。`gateway.approve()` 解除暂缓并更新固定摘要，之后调用再次成功。再看两次 `sync_upstream_ticket`：第一次的 `upstream_credential` 与客户端入站认证令牌相同，作为透传尝试被拒；第二次使用独立的上游凭据，调用成功。最后几次 `search_helpdesk` 超过配置的 `rate_limit` 四次上限，第五次尝试返回执行错误，不会悄悄排队或崩溃。可向 `SUSPICIOUS_PHRASES` 添加一个短语，注册描述含该短语的新工具，确认在任何调用发生前就完成隔离。

## 关键术语（Key Terms）

| 术语（Term） | 含义（Meaning） |
|------|---------|
| 元数据投毒（Metadata poisoning） | 工具名称、描述或注解中嵌入与工具职责无关的指令 |
| 获批后篡改（Rug pull） | 已批准工具的描述符发生变化，工具名称往往保持不变 |
| 定义固定（Definition pinning） | 批准时对完整描述符计算哈希，用于检测后续变化 |
| 工具遮蔽（Tool shadowing） | 多台服务器使用相同未限定工具名，导致发现顺序悄悄决定调用目标 |
| 混淆代理（Confused deputy） | 中间方被诱导使用受委托权限代攻击者行动 |
| 令牌透传（Token passthrough） | 将客户端面向 MCP 服务器的 bearer 令牌转发到无关上游 API |
| requestState 篡改 | 修改客户端本应原样回传的 MRTR 不透明状态 |
| SSRF | 服务器端请求伪造，诱导系统获取内部或非预期 URL |
| DNS 重绑定（DNS rebinding） | 域名验证时解析为安全地址，实际请求时却解析为内部地址 |
| 供应链漂移（Supply chain drift） | 注册表条目、软件包或运行端点在准入后独立发生变化 |
