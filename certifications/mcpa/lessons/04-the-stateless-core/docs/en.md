# MCP 的无状态核心（The Stateless Core of MCP）

> 每个请求都携带服务器作答所需的全部信息；即使沿用同一条连接，也不会从上一个请求继承任何协议状态。

**Type:** Reference
**Languages:** Python
**Prerequisites:** 第 03 课
**Time:** ~45 分钟

## 学习目标（Learning Objectives）

- 将无状态性解释为协议不变条件：每个请求都能自描述，服务器不得根据同一连接上的先前请求推断能力、版本或身份
- 解释无状态性的运维价值：任意副本都能响应任意请求，重试可被路由到其他副本，负载均衡器无须维持会话粘性
- 区分连接或 stdio 进程与会话或对话，说明列表结果与连接身份、当前请求所呈现授权之间的关系
- 按照 SEP-2567 模式，使用服务器生成的不透明显式句柄设计跨请求状态，让客户端将句柄作为普通工具参数传回
- 指出 2026-07-28 为将无状态设为默认而移除了哪些机制，并列出各自的替代方式

## 问题（The Problem）

在 2026-07-28 之前，连接 MCP 服务器意味着首先发送 `initialize` 请求。该请求协商协议版本、交换能力，并记录客户端和服务器身份；只要连接仍然存在，这些结果就作为会话状态保存。之后，同一连接上的每个请求都依赖握手建立的约定。只要还记得这些信息，服务器就无须反复确认“当前使用哪个版本”或“这个客户端支持什么”。

问题恰好在于这份记忆。绑定某条连接的会话，也绑定着维持该连接的进程。如果将一组服务器放在普通负载均衡器后，客户端的第二个请求可能落到另一个副本；这个副本从未见过握手，不知道先前协商了什么版本和能力。常见补救办法是粘性路由：在会话存续期间，把客户端固定到同一个后端。它通常能工作，直到该后端重启、部署新版本，或者相邻后端仍很空闲时它已过载。此时客户端的会话状态丢失，只能重新连接并再次握手。每个服务器作者都得编写代码，创建、跟踪并最终回收逐客户端的会话状态；每个客户端作者也得实现配套逻辑，以应对连接中断。这些复杂性并不服务于服务器真正承担的业务工作，而是会话机制引入并强制要求承担的额外开销。

## 概念（The Concept）

MCP 2026-07-28 采用无状态协议：处理请求所需的信息全部包含在该请求中。服务器独立处理每个请求，不得根据任何先前请求推断能力、协议版本或客户端身份，即使先前请求来自同一连接或流。第 03 课已经介绍支撑这一点的机制：每个请求都在 `params._meta` 中携带 `io.modelcontextprotocol/protocolVersion` 和 `io.modelcontextprotocol/clientCapabilities`，因此无须跨请求记住调用方是谁、支持什么。

```json
{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "add_item",
    "arguments": {"basket_id": "bsk_3f2a9c11", "sku": "tent"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

服务器即使此前从未见过这个客户端，即使进程中间处理过一千个不相关请求，也能够响应当前请求，并给出相同答案。关键就在这里：请求完整、独立地描述了需要完成的工作。

由此可以直接得出一个结论：打开的连接并不构成一段对话。stdio 进程或 HTTP 连接承载的是传输，传输本身不界定会话。客户端可以在同一传输通道上交错发送属于不同任务、用户或对话的不相关请求，服务器不得把连接或进程身份当作对话连续性的依据。同一个 stdio 进程中，某个用户的请求后面可能紧跟另一个用户的不相关请求；服务器必须正确处理两者，不能仅因它们从同一管道到达就假设彼此关联。

这一规则同样约束列表结果。`tools/list`、`resources/list` 和 `prompts/list` 的返回值不得因连接不同而变化，服务器也不得因为另一个请求的副作用而改变这些列表。例如，旧版服务器可能只有在同一连接上先调用 `connect_database` 后，才让 `query` 出现在 `tools/list` 中。允许列表变化的合理依据，是当前请求自身呈现的授权。如果服务器向低权限令牌返回较少工具，它读取的是当前请求的权限范围，这正符合无状态要求。绝不能做的是根据记忆中同一连接的先前请求所声明的信息，判断当前请求的权限范围。

无状态约束带来的运维收益值得这些设计纪律。既然请求不依赖任何进程内保存的协议记忆，负载均衡器后的任意副本就可以回答任意请求，普通轮询路由即可工作，无须粘性会话。某个请求中途失败后，也可以路由到另一个副本重试，无须寻找唯一记得先前状态的进程。副本崩溃或重启不会丢失协议所需的信息，因为这些信息本来就没有保存在那里。

这并不意味着服务器完全不能保存任何状态。购物篮、已打开的浏览器上下文、长时间运行的任务，都需要跨越多个工具调用持续存在。MCP 用显式的服务器生成句柄来处理这些状态，替代隐式会话。创建工具生成一个不透明标识符，通过 `structuredContent` 返回；模型随后携带这个标识符，在每次需要访问该状态的调用中，将其作为普通参数传回。

```json
// tools/call: create_basket
{"name": "create_basket", "arguments": {}}

// result
{
  "content": [{"type": "text", "text": "Created basket bsk_3f2a9c11"}],
  "structuredContent": {"basket_id": "bsk_3f2a9c11"},
  "resultType": "complete"
}
```

`basket_id` 的任何部分都不是协议专有机制。它只是工具结果中的普通字符串，以及工具参数中的普通字符串；从报文角度看，与工具返回的其他数据没有区别。协议不强制执行让句柄可靠工作的设计建议，因此这些责任落在服务器作者身上：保持句柄不透明，不在其中编码客户端可以解析或猜测的结构；每次调用都检查调用方是否有权访问该句柄，因为持有一个名称不等于获准使用它；在创建工具的描述中说明句柄存续时间，让模型决定是否创建状态之前就能看到策略。如果调用引用的句柄已经过期、从未存在，或属于其他调用方，应返回工具执行错误，即带有 `isError: true` 并解释问题的正常结果，不应返回 JSON-RPC 协议错误。句柄过期或不属于当前调用方，是模型可通过创建新购物篮来恢复的业务结果，并不意味着请求格式损坏。

这也回答了运行多个子智能体的编排器所关心的问题：列表结果不能取决于连接，因此同一已认证主体的第二条连接，例如编排器创建的子智能体，看到的 `tools/list` 与编排器相同，可以安全复用已缓存的列表，不必再次查询。按会话保存的列表无法提供这一保证，因为会话的设计本身就将它绑定到某一特定连接。

将无状态设为默认，需要移除有状态机制所依赖的基础设施。开场握手不复存在：`initialize` 请求和 `notifications/initialized` 均已移除，由每请求 `_meta` 和第 03 课涉及的可选 `server/discover` 调用替代。`Mcp-Session-Id` 请求头也已移除，因为不再有协议会话需要标识。能力不再以连接为范围保存，而是在每个请求中重新声明；服务器无须猜测三个请求之前记住的能力是否仍然有效。

## 交互实验（Interactive Lab）

图中两个客户端 alice 和 bob 经由轮询路由器，向 A、B 两个副本发送请求。两个副本都不在自身内存中保存购物篮状态，而是读写同一个共享存储，以创建工具返回的不透明句柄为键。因此，无论路由器下一次选择哪个副本，也无论此前由谁处理调用，结果都保持正确。追踪一个购物篮从创建到后续调用落在另一副本上的过程：答案不发生变化，交互本身也不会暴露其间涉及了两个不同进程。

## 实践实验（Practice Lab）

打开 `code/main.py`。它创建共享同一个 `SharedStore` 的两个副本，并用 `Router` 轮询分派请求，随后让三个调用方访问这套部署：alice、属于同一主体的 alice 第二条连接，以及属于另一主体的 bob。

```bash
python3 code/main.py
```

将打印出的交互与概念部分对照。Alice 的两条连接分别调用 `tools/list`，即使轮询路由器把请求交给不同副本，也会得到完全相同的工具列表。读取每个结果的 `_meta`，可以看到 `serverInfo.name` 在 `basket-replica-A` 与 `basket-replica-B` 之间变化，而 `tools` 数组逐字节保持一致。继续观察 alice 在一个副本上创建购物篮，再通过恰好路由到另一个副本的调用添加商品：添加成功，因为购物篮保存在共享存储中，而不局限于某一副本的内存。随后找出两个故意构造的失败。Bob 尝试向 alice 的购物篮添加商品，收到带有 `isError: true` 的正常结果，说明购物篮属于另一主体。之后，场景时钟推进至购物篮有效期之外，alice 的第二条连接尝试结算同一个购物篮，再次得到 `isError: true`，这次说明购物篮已经过期。两次失败都没有返回 JSON-RPC 错误，因为模型都可以据此采取行动：创建一个新购物篮后继续。

## 与综合实践的联系（Capstone Connection）

综合实践的端到端交互必须不受副本分配影响；其中长时间运行的任务和同意授权流程，都需要跨越多次往返。这些要求都建立在本课之上：服务器持有的状态，要么完全位于协议层之外，要么通过客户端在请求中显式传递的句柄引用。综合实践要求你说明设计为何能够安全水平扩展时，你将引用无状态核心，以及让状态能够脱离会话存在的句柄模式。

## 关键术语（Key Terms）

| 术语（Term） | 含义（Meaning） |
|------|---------|
| 无状态性（Statelessness） | 每个请求都能自描述，并独立于先前请求的协议不变条件 |
| 连接（Connection） | 传输层通道，例如 stdio 进程或 HTTP 连接，本身不构成会话或对话 |
| 副本（Replica） | 一组可互换服务器进程中的一个；因为不持有私有协议状态，任意副本都能响应任意请求 |
| 服务器生成句柄（Server-minted handle） | 创建工具返回的不透明标识符，后续作为普通参数传回，用于跨调用引用状态 |
| 共享存储（Shared store） | 所有副本共同读写的持久存储，使状态不局限于某一个进程内部 |
| 工具执行错误（Tool execution error） | 带有 `isError: true` 的正常结果，是报告过期、未知或他人句柄的正确通道 |
| `Mcp-Session-Id` | 旧版用于标识协议级会话的请求头，在 2026-07-28 中移除 |
