给定一份拟议的工具定义，按四步循环（描述、决策、执行、观察）审查，在工具交给模型之前标出会破坏循环的缺陷。

产出：

1. 名称审计（Name audit）。名称是否使用 `snake_case`，跨版本稳定且含义明确？标出与内置名称冲突、包含时态（“was_”“will_”）或嵌入参数的名称。
2. 描述审计（Description audit）。描述是否构成完整的使用说明？要求采用两句形式：“在 X 时使用。不要用于 Y。”标出少于 40 个字符的描述、营销文案或任何没有教会模型如何选择的内容。
3. 模式审计（Schema audit）。模式是否为有效的 JSON Schema 2020-12？每个字段是否有类型？`required` 列表是否明确？封闭值集是否使用枚举？标出本应使用枚举的开放字符串字段、缺失类型以及输入对象未声明 `additionalProperties` 的情况。
4. 执行器审计（Executor audit）。给定参数后执行器是否确定？是否用带类型的错误处理失败，而不是抛出逃逸宿主的异常？如果会产生实际后果（修改状态、花钱、接触用户数据），是否标明并放在确认门禁之后？
5. 分类（Classification）。说明工具是纯工具（Pure）还是产生实际后果的工具（Consequential），并解释原因。没有门禁的后者立即拒绝。

硬性拒绝条件：
- 描述只说做什么，不说何时使用的任何工具。模型在第二步需要“何时”。
- 含无类型字段的任何模式。校验器无法履行职责。
- 同时满足以下三项的任何工具：接受不可信输入、读取敏感数据、采取产生实际后果的行动。这违反 Meta 的二选规则（Rule of Two）。
- 执行器在错误输入下抛出未处理异常的任何工具。宿主不应需要为每次调用包裹 try/except。

拒绝规则：
- 工具定义缺少模式时，拒绝。先转到阶段 13 · 04。
- 工具是纯工具但描述说“谨慎少用”时，拒绝并询问原因。纯工具应能低成本重跑。
- 要求审查者批准一个访问生产数据库却没有只读防护的工具时，拒绝，并转到阶段 13 · 17（网关与策略）。

输出：一页审计报告，列出名称、描述、模式和执行器的发现，附严重程度（block / warn / nit），并给出最终结论 ship / revise / reject。如可行，最后用一行给被拒绝项提出改写建议。
